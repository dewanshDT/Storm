3 Crews inside the Storm v2 Agents page · chosen direction
This round puts crews into the approved Agents page with as little added as possible. Crews are collapsible sections in the existing sidebar, above the Running / Ended list, and the Overview shows one card per crew. Rows, marks, status badges, the session view and the closable, resizable Details panel are unchanged. A crew adds three things: a colour square, a name, and a small mono role tag on its members. Everything is drawn in Storm dark with the v2 tokens. Frames marked Phase 3 preview show orchestration that isn't in V1.

Interactions

What dropping does depends on the target. On a loose session, it makes a new crew; the name field opens for editing, prefilled from the shared context note or "New crew". On a crew header or member, it joins that crew. Between rows in a crew, it reorders. On Running or Ended, it leaves the crew. Crew headers can be dragged to reorder crews. Dropping never assigns a role.
3hPhone · launcher with Crew and Role
Started from the crew screen, so Crew is already set. Role defaults to None. Picking one adds that role's Kit note to the context, and the note under the fields says so.
3iSelect several → Make crew
⌘-click or Shift-click selects rows, and a bar appears at the foot of the sidebar. Esc clears the selection. This is the keyboard-friendly route to the same result as dragging.
3oStart work from this note → launcher creates the crew
This is the approved launcher with one new row. Opened from a note's Start session, it offers "New crew: {note title}" as a choice; the default stays None, so a plain session is still one click. A crew created here is only a label on the session, with no project or task attached. Role stays None unless you pick one.

With no crews, the sidebar is the approved Running / Ended list, and the overview shows one quiet hint above the sessions. The hint disappears after the first crew is made. With no sessions at all, the approved first-session and no-host states apply unchanged.

Skeletons without shimmer, as in the rest of Storm. Crew headers appear only once crews have loaded, so a session never jumps from loose into a crew while you're looking.

Two relationships, drawn differently
Crew membership · you decide · V1
Drawn as a section: a header with a colour square and name, and members inside it, set off by a single solid line on the left.
Any sessions can be grouped, related or not. You can move a session in, out or between crews at any time. It's only a label on the server.
Lineage · an agent started it · Phase 3
Drawn as a dashed indent under the parent, a "↳ from parent" sub-line, and a "started by …" link in the session header.
Lineage is fixed and can't be edited. If you move the child to another crew, the indent goes away there, but "↳ from …" and the header link stay, so the relationship is never lost.
Decided
1. Roles aren't unique seats. Several sessions can have the same role. A role describes the kind of work a session does; it doesn't define a team structure.
2. Role tags are neutral. Mono text in a 1px outline: solid when you set the role, dashed when an agent did. The crew colour is the only colour a crew adds. No colours come from Kit notes.
3. Membership and lineage are separate. A crew is a coloured section with a solid left edge. A child session sits on a dashed indent with "↳ from …" and "Started by". Both appear on desktop and phone.
4. The default is collapsible sections, with sessions that aren't in a crew listed below. The crew page is the focused view for one crew.
5. Spawning isn't in the shipped experience. It appears only in frames labelled Phase 3 (3m, 3n, 3p).
Still open
• Collapse state: per device (like the Details panel width) or synced? I've assumed per device.
• Empty crews: once every member is dismissed, delete the crew (with a few seconds of Undo) or keep it? Round 1 assumed it's deleted.
• Name for a crew made by dragging when the two sessions have different context notes: use the target's note, or always "New crew"?
1. Can a role note declare "one per crew"? Recommended: not in V1. Duplicate roles are allowed, and the crew page simply lists both. If yes (for example a per_crew: 1 property), the launcher and the move sheet must grey out a role that's taken and explain why, a drag can be refused, and Storm starts enforcing rules written in notes. That's a new kind of coupling between Kit content and app behaviour. Unresolved.
2. Role colours. Recommended: neutral tags. Mono text in a 1px outline, solid if you set the role and dashed if an agent did. The crew's colour square is the only colour a crew adds. If role colours came from Kit metadata, the colours would compete with status (accent = running, danger = failed), break the rule that each colour has one meaning, and a badly chosen colour in a note could fail contrast. Unresolved.
3. Membership vs lineage. Recommended: section vs dashed indent, as described above. If lineage defined the crew (1c), you couldn't group unrelated sessions. If only a tag showed lineage, a parent with three children would look like four unrelated sessions. Unresolved; this only affects Phase 3.
4. Default view. Recommended: collapsible sections plus a crew page (3a, 3c). A board (1b) brings in a Kanban reading and hides loose sessions. A tree with a separate members view (1c) needs two screens for one crew and depends on lineage. Unresolved.
5. Show the spawning setting before Phase 3? Recommended: hide it until the capability ships. Showing a disabled row would promise something that doesn't exist yet. If it's shown early, it has to stay off and say "not available yet". Unresolved.
What it takes to build
• UI only: sections, collapse state (kept per device, like the Details panel width), drag and drop, multi-select, the long-press sheet, and role tag styling.
• New server work, V1: a crew object (name, colour word, order) and membership (session, order, role note id, who set it), synced like sessions. Also: the launcher passing the role note as extra context, and End all / Dismiss all, which can loop over the existing calls.
• Already depends on v2 server work: the crew page's Started from and Wrote lists come from each session's context note and Wrote list, which the v2 handoff already marks as new API.
• Phase 3, not designed for V1: agents starting sessions, a parent link on sessions, the approval prompt, and the "Let agents start agents" setting.

Rules
• Plain by default. A session has no role unless one is set in the launcher, or by the agent that started it. Dragging a session into a crew doesn't give it a role.
• Who set the role is visible. A solid tag means you set it; a dashed tag means an agent did. About shows "set by …". You can change or clear any role later, and the tag turns solid once you do.
• No required Lead. A crew can be all plain members. Lead is a role like any other, coming from its Kit note.
• Agent-started sessions join the crew of the session that started them, nested under it. If the starter isn't in a crew, a crew is created around it and named after the starter's context note.
Decided
1. Agents starting agents. A started session never gets more access than the session that started it: the same vaults or fewer, the same write vault or none, and the same integrations. Each start waits for your approval, unless you've turned on Let agents start agents in Settings › AI access, under Storm agents (off by default). The approval prompt shows the same access summary as the launcher.
2. Backend. This needs a new Storm tool that lets an agent start a session (host, workspace, agent, role, parent), plus a "started by" link on sessions. It's orchestration work, planned for Phase 3, and it isn't in V1.
3. Roles come entirely from Kit. The role list is every note in Kit's agents/ folder, read live, with nothing built in. Lead, Coder and Reviewer exist only because Kit is seeded with those notes.
What follows from roles being dynamic
• A role is a link to its Kit note, stored by the note's id, not its name. Renaming the note renames the role everywhere. The tag shows the note's title in capitals.
• Deleted role note: sessions keep the tag, struck through and dimmed, with "Role note was deleted" in About. You can clear it or pick another role. Nothing breaks, and nothing changes silently.
• "Lead" is no longer special in code. Earlier rounds had a one-Lead-per-crew rule; with roles coming from notes there's no built-in Lead to enforce it on. Any limit would have to come from the note itself, which is an open question (below).
• No Kit vault, or an empty agents folder: the Role row offers only None, with "Add roles in Kit ›".
• Launching with a role gives the agent that role's note as context, alongside any context note you picked. Dragging a session in, or setting a role after launch, only sets the label (open question 1 from round 1, now resolved).
Still open
• One-per-crew limits. Should a role note be able to say "one per crew", for example with a property like per_crew: 1? If not, a crew can have two Leads.
• Role colour. Should the tag pick up the role note's colour property? It uses the existing vault palette words, so it needs no new tokens.
1 Agent crews: three grouping models

Ungrouped sessions stay in a plain Running / Ended list below the crews. Inside a crew, running sessions come before ended ones, and ended sessions stay dimmed until you dismiss them. All three models use the same creation paths and group actions; they differ in how a crew is shown and what you drag onto what.

Creating a crew
• Drop a session onto another. Both join a new crew, and the session you dropped onto becomes the Lead. The crew is named after the Lead's context note, or "New crew" if there isn't one. The name field opens straight away for editing.
• Select several, then Group. ⌘-click or Shift-click rows, and a bar appears at the foot of the sidebar: "3 selected · Make crew". The first session you selected becomes the Lead.
• From the launcher. Choose "New crew…", and the session you're launching becomes its Lead.
• From a note. "Start work from this note" opens the launcher with Crew set to a new crew named after the note, and Role set to Lead.
Group actions: New session in crew (the launcher opens with this crew set, with Role defaulting to Coder) · End all running (one confirmation that lists every session it will stop) · Dismiss all ended · Rename · Colour (vault palette) · Collapse.
Dragging: move a session into or out of a crew, reorder sessions within a crew, and reorder crews. On the phone, there's no dragging: long-press a session to Move to crew or Change role.
Server: crews need a new object and API (id, name, colour, order, plus members as session id, role and order). A crew is only a label: sessions never move hosts, and a crew has no effect on what an agent can access.
Open questions
1. Does a role do anything? One option is that a role is only a label. The other is that launching with a role also gives the agent the matching Kit role note (Storm Lead, Coder, Reviewer) as context. I'd suggest the second for sessions you launch, and label-only for sessions you drag in, because a running session can't take on new context.
2. Which roles? Lead, Coder and Reviewer, taken from Kit's role notes, which would also bring in Architect and Researcher. A crew has one Lead and any number of the other roles.
3. When the Lead ends: the crew stays, and nothing stops automatically, because there's no cascade-stop in V1. When the Lead is dismissed, the next member becomes Lead. This matters most for 1c.
4. An empty crew, once every session is dismissed, is deleted automatically, and Undo appears for a few seconds.
